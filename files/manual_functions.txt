25. secure_store_plaid_token ⭐ ACTIVE
   - Securely stores Plaid access token in Vault
   - Parameters: p_item_id (text), p_user_id (uuid), p_token (text)
   - Returns: uuid (secret_id)
   - Purpose: Encrypted storage of banking credentials
   - Used in: store-plaid-token function
   - Notes:
     * Automatically deletes old secret from Vault before creating new one (prevents orphaned secrets)
     * Deletes by both secret_id (from user_items.access_token_secret_id) and by name ('plaid_' || item_id)
     * Ensures no duplicate secrets exist for the same item_id

26. secure_delete_plaid_token ⭐ ACTIVE
   - Securely deletes Plaid access token from Vault
   - Parameters: p_item_id (text), p_user_id (uuid)
   - Returns: void
   - Purpose: Removes encrypted Plaid tokens when accounts/items are deleted
   - Used in: plaid_management.js (remove_item and remove_account modes)
   - Notes:
     * Deletes secret from Vault using DELETE FROM vault.secrets (Supabase doesn't provide vault.delete_secret() function)
     * Attempts deletion by both secret_id (from user_items.access_token_secret_id) and by name ('plaid_' || item_id)
     * Clears access_token_secret_id from user_items table after successful deletion
     * Critical for security compliance - ensures tokens are removed when users disconnect accounts

NOTES:
- ⭐ ACTIVE functions are currently used in the codebase
- All functions use Row Level Security (RLS) where applicable
- Functions with p_user_id parameter automatically filter by authenticated user
- Date parameters use PostgreSQL date type for consistency
- Numeric parameters use PostgreSQL numeric type for precision
- Functions return TABLE types for complex result sets
- Security functions use Supabase Vault for encrypted credential storage
  * Vault secrets are deleted using DELETE FROM vault.secrets (no built-in delete_secret() function)
  * secure_store_plaid_token automatically cleans up old secrets to prevent orphaned entries
- Automatic categorization functions work with triggers for real-time categorization
- Chat history functions use JSONB for efficient message storage and retrieval
- Trigger functions are automatically executed by PostgreSQL triggers
- Category rules now support both merchant_name-based and name-based matching (fixes Zelle NULL merchant_name issue)
- Investment functions support both detailed table returns and JSONB overview format
- Cleanup functions should be run periodically via scheduled jobs or cron
- User deletion function (hard_delete_user) is irreversible and should be used with extreme caution
