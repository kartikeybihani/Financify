# Recurring Section - Complete Analysis
# Finny Codebase - February 2025
# schmea - @tables.txt file

================================================================================
1. SCHEMA OVERVIEW
================================================================================

recurring_streams TABLE:
- Source: Plaid API (transactionsRecurringGet) → stored via refreshAndStoreRecurringForItem
- Key columns: stream_id, stream_type (subscription|income|bill|other), transaction_ids (JSON array), is_active, user_dismissed

transactions TABLE:
- recurring_stream_id: FK to recurring_streams.stream_id (links tx to a Plaid stream)
- if_recurring: 'yes' | 'no'

================================================================================
2. WHERE DOES THE RECURRING SECTION DATA COME FROM?
================================================================================

Data source: getRecurringTransactionsFromDatabase (plaid.ts)
- Fetches recurring_streams where is_active=true AND user_dismissed=false
- Also fetches user-marked recurring: transactions with if_recurring='yes' AND recurring_stream_id IS NULL
- User-marked are grouped by merchant/name into virtual streams (stream_id: user-marked-group-{hash})

What shows in the Recurring section:
1. Plaid streams (subscriptions, income, bills, other)
2. User-marked recurring (grouped by merchant name)

================================================================================
3. HOW PLAID STREAMS GET INTO THE SYSTEM
================================================================================

When: Plaid webhook (DEFAULT_UPDATE, etc) or manual refresh (refresh_financial_data.js)

Flow (lib/plaid/recurringRefresh.js):
1. Call Plaid transactionsRecurringGet
2. Categorize into subscription/income/bill/other (category + merchant keywords)
3. Mark all existing streams for item as is_active=false
4. Upsert new stream rows (user_dismissed preserved on conflict)
5. backfillRecurringCategories: For each stream, if NOT user_dismissed, update transactions with recurring_stream_id, if_recurring='yes', and optionally new_category

================================================================================
4. TRANSACTION SYNC AND RECURRING
================================================================================

Sync sources: Supabase edge function (sync-transactions), api/transactions_sync.js, api/scheduled-sync.js

During sync:
- Fetch recurring_streams (is_active, !user_dismissed)
- Build map: plaid_transaction_id -> stream
- For each added/modified transaction: if in map → set recurring_stream_id, if_recurring='yes'
- transactions_sync.js also: NEW transactions matching stream by txn.name === stream.description get linked and added to stream's transaction_ids (streamUpdates)

User override protection: If tx NOT in stream but user had if_recurring='yes' → preserve it

================================================================================
5. USER MARKS A TRANSACTION AS RECURRING
================================================================================

Where: Transaction detail modal toggle → bulkUpdateRecurringStatus (recurringBulkUpdate.ts)

Flow:
1. Find similar transactions (by recurring_stream_id first, else merchant_name/name)
2. Bulk update: if_recurring='yes', recurring_stream_id=null (user-marked = no stream_id)
3. Clear recurring cache, emit events → Recurring section refetches

Result: All similar past transactions get if_recurring='yes'. They appear as user-marked stream. Future new transactions with same merchant are NOT auto-marked (no merchant-based matching for user-marked in sync).

================================================================================
6. USER CLICKS REMOVE (RECURRING SECTION)
================================================================================

Flow (RecurringSection.tsx handleRemoveRecurring):
1. If Plaid stream: dismissRecurringStream(userId, stream_id) → sets user_dismissed=true
2. bulkUpdateRecurringStatus(..., "no", clearRecurringStreamId=true) on all similar tx

What happens to FUTURE transactions?
- Plaid refresh: backfillRecurringCategories skips user_dismissed streams → no re-application
- Transaction sync: Only fetches streams with user_dismissed=false → dismissed stream not used
- Result: Future transactions from that Plaid stream will NOT be marked recurring ✓

For user-marked: No stream row. Remove just sets if_recurring='no' on past tx. Future similar tx were never auto-marked anyway.

================================================================================
7. SUMMARY TABLE
================================================================================

Action                    | Plaid stream                           | User-marked stream
--------------------------|----------------------------------------|----------------------------------------
Shows in Recurring        | Yes (unless user_dismissed)            | Yes (grouped by merchant)
Future tx auto-marked?    | Yes (until Remove)                     | No
Remove does               | user_dismissed + bulk if_recurring=no  | Bulk if_recurring=no only
After Remove, future tx   | NOT re-marked ✓                        | N/A (were never auto-marked)

================================================================================
8. EDGE CASES / GAPS
================================================================================

1. User marks as recurring → creates user-marked stream. Future tx with same merchant are NOT auto-marked (no name-match logic for user-marked).
2. No "restore" after Remove — user would need to mark again.
3. Plaid can drop streams; we mark inactive. Dismissed streams stay in DB with user_dismissed=true.
4. Name matching (txn.name === stream.description) in transactions_sync is loose; could match wrong stream if descriptions overlap.
5. Race: recurring refresh vs transaction sync can run in different order; both update tx, but ordering can cause brief inconsistencies.

================================================================================
9. MENTAL MODEL (TL;DR)
================================================================================

- Plaid streams = source of truth from Plaid, stored in recurring_streams
- user_dismissed = "user said don't show this, and don't re-apply recurring to its transactions"
- User-marked = if_recurring=yes + no stream_id, grouped on read
- Remove = for Plaid: dismiss stream + clear tx; for user-marked: clear tx only
- Future transactions only get auto-marked by Plaid streams (non-dismissed); user-marked has no auto logic
